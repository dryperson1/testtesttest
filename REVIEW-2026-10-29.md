# Review of the code against the product brief (2026-10-29)

**For:** the product owner. **Question:** is the code on the right track to what [PRODUCT.md](PRODUCT.md) describes, what must change, and in what order?

**How it was done.** Twelve read-only checks compared the code with the brief (checklist items 1 to 10, the AI session, the 15-minute promise). A skeptic then tried to refute every "must change" finding; refuted findings carry the skeptic's corrected severity here. Item 11 (effects as plug-ins) is left to the approved plug-in block work, and the defect review waits until after it (owner's decision D4). Nothing in the project was changed apart from this file.

**Words used.** *Blocks*: the brief cannot be met as the code stands. *Needs change*: required, with time to do it. *Harmless* or *fine*: no change required. *Small* is days, *medium* one to three weeks, *large* longer. Evidence is in the appendices.

---

## 1. Verdict

1. Yes, the code is on the right track. Edits are pure and replayable, the gestures can be sent by an AI, a project is one file, footage is referenced and never copied, and slow work runs as background jobs. No stored format has to be thrown away.
2. One thing blocks the brief. On the 16 GB laptop the brief names as the floor, a 4K export of a fast-cut hype edit would keep about ten FFmpeg decoders of about 1 GB each open, because decoder limits count decoders, not memory.
3. Four cheap fixes should follow soon:
   - saves and undo freeze for seconds on long projects;
   - background jobs ignore their CPU share;
   - the preview skips proxies on most laptop screens;
   - the design documents still plan optional cloud AI and would give the planner every command schema.
4. The rest are missing features, not wrong code: chat storage, marking AI and hand edits, captions, HDR, model choice, simple mode, keyboard selection. Each has a rule to settle before it is built.
5. Of 75 "must change" findings, the skeptic downgraded 44 and upheld 9. The other 22 got no verdict, so I checked the ones this report relies on and re-measured the blocker myself.

## 2. What blocks the brief

### B1. Decoder memory is limited by count, not bytes

**Evidence.** Playback allows 4 decoders per file and 16 in total, and closes one only after 300 frame requests have gone elsewhere (`crates/playback/src/frames.rs:22,25,30`). That check runs only when a frame is requested (`frames.rs:1545`), so nothing closes while paused. Export raises the per-file limit to at least 16 (`crates/export/src/frames.rs:119-128`), and FFmpeg runs with no thread limit (`crates/media/src/decode.rs:529-554`). One 4K 10-bit HEVC decoder, left waiting after three frames as the player leaves it, holds 0.99 GB with 8 threads and 1.35 GB with automatic threads (my measurement; the laptop check got 1.0 and 1.37 GB).

In a hype edit cut about every second from one long recording, each cut starts a new decoder while the previous one waits about ten seconds to close: roughly ten open at once, about 10 GB, plus the encoder and the paused player's decoders. The laptop check estimates 12 to 14 GB in total with a hardware encoder and 16 to 20 GB with AV1. This is worked out from the code and per-decoder measurements, not seen in a running export; no test plays or exports 4K end to end.

**Why it blocks.** The brief requires 4K export (`PRODUCT.md:121`) on a 16 GB machine (`PRODUCT.md:21`), and hype edits come first. With Windows using 3.5 to 4.5 GB, the export does not fit: it pages heavily or fails. The brief accepts slower on weak machines (`PRODUCT.md:138`), not failing.

**Change.** A memory budget sized from the machine's RAM instead of counts; a thread limit on every decoder; idle decoders closed after a time and on pause; in export, a decoder closed once no later clip reads on from it; a 4K export test that records peak memory. **Size:** small to medium, about a week. **Plug-in plan:** does not touch decoders. **Status:** rated "blocks", no skeptic verdict; I verified the code and re-measured.

**Two more fixes in the same code, done in the same pass** (both *needs change*):
- **The preview frame cache counts frames, not bytes.** It holds 96 frames (`ui/src-tauri/src/player.rs:860`), about 3 GB at a 3840-pixel-wide preview. Give it a byte limit. Upheld by the skeptic.
- **The preview skips proxies on most laptop screens.** A proxy is used only when the wanted picture size fits inside it (`crates/playback/src/frames.rs:1438-1449`), and proxies are 540 lines tall. So an M1, or any preview wider than 960 device pixels, decodes the 4K original instead. Use the proxy while playing and scrubbing, and decode the original only for a paused frame once it has settled. This is what makes "smooth editing through proxies" (`PRODUCT.md:120`) true on laptops. No skeptic verdict; I confirmed the rule in the code.

**Item 3 (saves and undo freezing)**
- `live_blob_keys` (`crates/core-project/src/lib.rs:359-366`) runs on every save (`lib.rs:430-433`) and on every undo or redo past the checkpoint (`lib.rs:325-328,343`).
- History holds up to 500 steps (`crates/core-commands/src/store.rs:41`).
- Autosave runs every 50 edits or after 30 s idle (`ui/src-tauri/src/settings.rs:134-140`), under the project lock.
- `history_jump` undoes one step at a time (`ui/src-tauri/src/service/edit.rs:450-469`).
- At 2,000 clips the cost is about 0.35 s per checkpoint (skeptic).

**Item 4 (design documents)**
- **Cloud:** `docs/ARCHITECTURE.md:155,247,316,318,341,827,842`; `docs/LOCAL-FREE-DECISIONS.md:13,40`. A local address alone does not prove the work stays local, because a local runtime can forward requests to a cloud service.
- **Planner prompt:**
  - `README.md:139`.
  - Schema sizes: `schemas/Command.schema.json` 65,678 bytes, `Transaction.schema.json` 71,920 bytes, `EditOp.schema.json` 20,485 bytes.
  - An 8B model on a laptop processor reads about 30 to 60 tokens per second (15-minute check's estimate).
  - Proposed instead: compact skill schemas, a stable prefix that can be cached, block parameters fetched only when used, and deterministic skills placing the clips.

**Item 11 (HDR)**
- Decoding always outputs 8-bit RGBA (`crates/media/src/decode.rs:554`).

- The output target is 8-bit and clamped (`crates/render/src/gpu.rs`, `output.wgsl`).
- The encoder pipe reads RGBA (`crates/media/src/encode.rs:1646`), and BT.709 tags are always written (`encode.rs:661-670`).

- **Caveats on the proposed packed 10-bit format:**

  - it changes the pixels of 10-bit SDR footage, which goes against decision D1.
